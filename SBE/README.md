# SBE — Sealed Branch Eval

SBE is the repository's end-of-task containment and verification method.

## Contract

1. The authoritative task specification exists on `main` at `SBE/requests/<request-id>.json` before the processing PR is opened.
2. The processing branch is named exactly `processing/<request-id>`.
3. Relative to the PR base, the processing branch contains exactly one changed submission file and that file is an added or modified `.gz` file.
4. A pull request targets `main` from the same repository.
5. `SBE Seal Submission` reads trusted SBE code from `main`, treats the PR head only as untrusted data, and performs **no Gemini evaluation before sealing**.
6. The workflow immediately wraps the submitted `.gz` in a header-encrypted 7z archive using the user-controlled `GZ_PASSWORD` repository secret.
7. The encrypted artifact plus a non-content manifest are persisted to `main` at `SBE/sealed/<request-id>/<source-head-sha>/`.
8. The workflow removes the submitted `.gz` from the processing branch and replaces it with `.delete-processing-branch`.
9. `SBE Delete Processing Branch` runs after successful sealing. It verifies the marker, verifies that the marker commit is directly descended from the submitted commit and contains only the expected submission deletion plus marker addition, and verifies the sealed artifact exists on `main`.
10. After those checks, it closes the pull request without merge and deletes the processing branch.
11. **Only after the processing branch has been deleted** does the workflow decrypt the password-protected artifact in ephemeral runner storage and begin completion evaluation.
12. The workflow generates a fresh 64-hex-character evaluation nonce for that specific evaluation run.
13. Gemini receives the authoritative request, completion criteria, submission, and nonce. Its accepted return schema is exactly `{"result":"PASS|FAIL","nonce":"<exact supplied nonce>"}`.
14. Gemini does not validate its own return. `sbe-validate-evaluator-return.js` mechanically validates the raw evaluator return. It requires exactly one JSON object, exactly the keys `result` and `nonce`, `result` equal to `PASS` or `FAIL`, and an exact nonce match.
15. If mechanical validation fails, the workflow sends the evaluator a correction payload containing **the complete original evaluator payload, the evaluator response that failed, the exact mechanical validation failure, and an exact valid return-schema example using the current nonce**. The correction package is not printed to workflow logs.
16. The workflow mechanically validates the corrected evaluator return again. A structurally valid `FAIL` is not a schema failure and is not repaired; it is the evaluator's completion verdict.
17. On a structurally valid evaluator return, the workflow creates the nonce-bound evaluation record. That record is encrypted with `GZ_PASSWORD` and stored as `evaluation.7z` beside the sealed submission. The manifest records only non-content metadata, `evaluation_status`, `evaluation_nonce`, and the evaluation archive path.
18. A successful SBE completion claim requires the sealed artifact to exist on `main`, the PR to be closed without merge, the processing branch to be deleted, and the mechanically validated post-delete Gemini result to be `PASS` with the exact nonce for that evaluation run.

## Authoritative request schema

```json
{
  "request_id": "example-id",
  "request": "Verbatim task/request to be evaluated.",
  "completion_criteria": [
    "Optional explicit completion criterion"
  ]
}
```

`request_id` must match the branch suffix in `processing/<request-id>`.

## Accepted evaluator return

The raw evaluator response must itself be valid JSON and contain no additional prose or fields. For a supplied nonce, the exact shape is:

```json
{"result":"PASS","nonce":"<exact supplied nonce>"}
```

`FAIL` is also valid for `result`. The nonce must exactly match the nonce generated by the workflow for that evaluation run.

## Invalid-return correction payload

When the raw evaluator return fails deterministic validation, the evaluator is given these four components:

```json
{
  "original_payload": "<complete original evaluator payload>",
  "response": "<raw invalid evaluator response>",
  "validation_check_failure": "<exact deterministic failure>",
  "exact_return_schema_example": {
    "result": "PASS",
    "nonce": "<exact current nonce>"
  }
}
```

The workflow, not Gemini, performs validation of the corrected response again.

## Security boundary

The plaintext submission may exist in the temporary processing branch and ephemeral runner only until it is sealed. It is never merged into `main`. The durable submission artifact on `main` is password-encrypted. Branch deletion is lifecycle cleanup; the cryptographic protection comes from `GZ_PASSWORD` encryption.

Gemini evaluation occurs only after sealing and branch deletion. Privileged repository writes remain under deterministic workflow control rather than model control. Raw evaluator exchanges and invalid-return correction payloads remain ephemeral and are not committed to the repository.
